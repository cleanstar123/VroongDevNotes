- **작성일:** 2026-08-05
- **관련 분석 파일:** `헥토_출금_기록_누락_장애_분석.md`

## 1. 해결 방향 결정

### 근본 문제

Hecto API 성공 후 DB 저장 시 RDS가 불가 상태이면 기록이 영구 소실된다.
`vr_withdrl_list`, `vr_account_mst` INSERT가 하나의 트랜잭션으로 묶여 있어
DB 장애 시 재처리 수단이 전혀 없었다.

### 해결 전략

**PENDING Guard 패턴 + 복구 배치** 조합으로 해결.

```
[Hecto API 호출 전]
  PENDING 레코드를 먼저 DB에 독립 커밋 (REQUIRES_NEW)
  → 이 시점부터 라이더의 중복 출금 요청 차단

[Hecto 성공 후]
  W/F 원장 기록 후 COMPLETED 갱신 (각각 REQUIRES_NEW)
  → 어느 단계에서 DB 장애가 나도 PENDING이 남아 있음

[복구 배치 (5분 주기)]
  PENDING/UNKNOWN 레코드 중 10분 경과 건 조회
  → 헥토 결과조회(fxResult) API 호출
  → 성공(status=21): W/F 재삽입 + COMPLETED
  → 실패(22)/취소(23): FAILED/CANCELLED
  → 처리중(29): 건너뜀, 다음 배치 재시도
```

## 4. 핵심 구현 상세

### 4-1. PENDING 레코드 저장 (Hecto 호출 전)

`WithdrawRequestLogService.savePending()` — `REQUIRES_NEW`로 독립 커밋.

```
[외부 @Transactional (requestWithdrl)]
  ├── getWithdrlAccountInfoWithLock()  ← 비관적 락 획득
  ├── 잔액/수수료 검증
  ├── savePending() [REQUIRES_NEW] ← DB 커밋 ①
  ├── hectoPaymentWebClient.requestWithdrawal().block()
  ├── saveWithdrawlRecords() [REQUIRES_NEW] ← DB 커밋 ②
  └── updateWithResponse("COMPLETED") [REQUIRES_NEW] ← DB 커밋 ③
```

외부 트랜잭션은 비관적 락 관리만 담당. 모든 쓰기는 REQUIRES_NEW 독립 커밋.

### 4-2. W/F 저장 실패 처리 (Bug 1 수정)

**기존 코드 문제:** W/F 저장 실패 여부와 무관하게 COMPLETED를 갱신했음.
→ W/F 누락 상태로 COMPLETED가 되면 복구 배치 대상에서 제외되어 영구 누락.

**수정 후:**
```java
boolean wfSaved = false;
try {
    withdrawRequestLogService.saveWithdrawlRecords(pendingSeqNo, withdrawCtx);
    wfSaved = true;
} catch (Exception ex) {
    log.warn("W/F 저장 실패 - STATUS=PENDING 유지, 복구 배치 대상: pendingSeqNo={}", pendingSeqNo, ex);
}
if (wfSaved) {
    try {
        withdrawRequestLogService.updateWithResponse(pendingSeqNo, withdrawalResponse, "COMPLETED");
    } catch (Exception ex) {
        log.warn("COMPLETED 갱신 실패 (복구 배치 대상): pendingSeqNo={}", pendingSeqNo, ex.getMessage());
    }
}
```

W/F 저장 실패 시 PENDING 유지 → 10분 후 복구 배치가 W/F 재삽입 + COMPLETED 처리.

### 4-3. VTIM (은행 타임아웃) 처리

Hecto 공식 스펙: `outRsltCd=VTIM`은 은행 타임아웃으로 **송금이 실제로 됐을 수 있음**.
반드시 결과조회 후 성공/실패 확인 필요. FAILED로 처리하면 이중 손실 위험.

```java
if ("VTIM".equals(withdrawalResponse.getOutRsltCd())) {
    withdrawRequestLogService.updateStatus(pendingSeqNo, "UNKNOWN");
    throw new RuntimeException("헥토 출금 결과 미확정 (은행 타임아웃). 잠시 후 내역을 확인해주세요.");
}
```

UNKNOWN → 복구 배치가 fxResult 조회 → status=21이면 COMPLETED 처리.

### 4-4. 복구 배치 이중 처리 방지 (Bug 2 수정)

**기존 코드 문제:** 배치에서 엔티티를 re-fetch한 후 STATUS 검증이 없어
다른 스레드/배치가 이미 처리한 건을 중복 처리할 수 있었음.

**수정 후:**
```java
VrWithdrawRequestHisEntity entity =
    mobWithdrlQueryDslRepository.findWithdrawRequestHisBySeqNo(seqNo);
// 다른 스레드/배치가 이미 처리한 경우 재처리 방지
if (!"PENDING".equals(entity.getStatus()) && !"UNKNOWN".equals(entity.getStatus())) {
    log.info("[복구배치] 이미 처리된 레코드, 건너뜀: seqNo={}, status={}", seqNo, entity.getStatus());
    return;
}
```

### 4-5. fxResult 엔드포인트 수정

**기존 코드 오류:** `/pyag/v1/fxResultKrw` (존재하지 않는 엔드포인트)

**수정:**
- 엔드포인트: `/pyag/v1/fxResult`
- 파라미터 변경: `trdDt`(현재시각), `trdTm`(현재시각) 제거 → `orgTrdDt`(원거래일자) 추가
- `orgTrdDt`: `pending.getInsDate()`에서 추출 (헥토 호출 시점 = PENDING 생성일)

```java
// 수정 전 (잘못됨)
queryResult(mchtTrdNo)  // trdDt=현재, trdTm=현재 전송

// 수정 후
queryResult(mchtTrdNo, orgTrdDt)  // orgTrdDt = pending.getInsDate() 기반
```

## 5. 헥토 공식 문서 교차 검토 (fxResult)

**(헥토파이낸셜) 지급대행_원화송금_연동규격서_20240920** 기준으로 직접 비교.

### 요청 파라미터

| 파라미터 | Max.Len | 설명 | 현재 구현 |
|---------|---------|------|----------|
| `mchtId` | 12 | 상점아이디 | ✅ 전송 |
| `mchtTrdNo` | 100 | 원거래 상점 거래번호 | ✅ 전송 |
| `trdNo` | 40 | 헥토발급 거래번호 (mchtTrdNo 또는 trdNo 중 1개 필수) | ✅ 미전송 (mchtTrdNo만으로 충분) |
| `orgTrdDt` | 8 | 원거래일자 | ✅ PENDING insDate 기반으로 전송 |

### 응답 status 처리

| status | 의미 | 현재 처리 |
|--------|------|----------|
| `21` | 송금성공 | ✅ COMPLETED + W/F 재삽입 |
| `22` | 송금실패 | ✅ FAILED |
| `23` | 송금취소 | ✅ CANCELLED |
| `29` | 처리중 (은행 타임아웃) | ✅ 건너뜀, 다음 배치 재시도 |
| `00` | 요청데이터 오류 | ✅ FAILED (else 분기) |
| `99` | 미정의 오류 | ✅ FAILED (else 분기) |

### 문서 샘플의 `"status":"0"` 이슈

공식 문서 응답 샘플:
```json
{"outStatCd":"0021","outRsltCd":"0000","outRsltMsg":"정상처리","status":"0"}
```

문서 작성자 오기로 판단 (같은 샘플에서 outStatCd=0021, outRsltCd=0000으로 성공임이 명확).
정의된 status 코드 중 `"0"`은 없음.

**방어 처리 추가:**
```java
// status="0" 오기 방어 — outStatCd/outRsltCd로 이중 확인
boolean isSuccess = "21".equals(status)
    || ("0021".equals(result.getOutStatCd()) && "0000".equals(result.getOutRsltCd()));
```

## 6. 정상 출금 흐름 검토 결과

### 트랜잭션 구조

모든 쓰기 메서드가 `REQUIRES_NEW` → 외부 트랜잭션 롤백과 무관하게 독립 커밋.
외부 `@Transactional`은 비관적 락(SELECT FOR UPDATE) 관리만 담당.

### 동시 요청 시뮬레이션

```
요청A: hasPendingCheck=false → getWithdrlAccountInfoWithLock() [락 획득]
요청B: hasPendingCheck=false → getWithdrlAccountInfoWithLock() [락 대기]
요청A: PENDING 커밋 → Hecto → W/F 커밋(잔액 차감) → COMPLETED → 락 해제
요청B: 락 획득 → 잔액 재조회 (A의 차감 반영됨) → 잔액 검증 → 진행 또는 거절
```

비관적 락이 잔액 검증을 직렬화하므로 이중 출금 불가. ✅

### 장애 시나리오별 결과

| 장애 시점 | 결과 | 복구 |
|----------|------|------|
| PENDING 저장 전 예외 | 출금 요청 자체 실패, DB 변경 없음 | 사용자 재시도 가능 |
| PENDING 저장 후 Hecto 호출 전 예외 | PENDING 남음 (10분 후 복구 배치) | fxResult 조회 → Hecto 거래 없음 → FAILED |
| Hecto 통신 오류/타임아웃 | STATUS=UNKNOWN | 복구 배치 → fxResult 결과에 따라 처리 |
| Hecto VTIM | STATUS=UNKNOWN | 복구 배치 → fxResult=21이면 COMPLETED |
| W/F 저장 실패 | STATUS=PENDING 유지 (wfSaved=false) | 복구 배치 → W/F 재삽입 + COMPLETED |
| COMPLETED 갱신 실패 | W/F 있음, STATUS=PENDING | 복구 배치 → existsWithdrlListByHisSeqNo=true → STATUS만 COMPLETED |
| 정상 완료 | PENDING → COMPLETED, W/F 기록 | 복구 배치 대상 아님 (10분 미경과) |

## 7. 복구 배치 스케줄

- **위치:** `3pl-platform-batch` 모듈
- **실행 주기:** 5분마다 (Quartz CronTrigger, `triggerType=WITHDRAWAL_RECOVERY`)
- **대상 조건:** STATUS=PENDING 또는 UNKNOWN, INS_DATE < 현재 - 10분
- **최대 처리 건수:** 100건/회 (setMaxResults)

## 8. 배포 순서

DB 컬럼 추가 → relay-server → api → 3pl-platform-batch 순으로 배포.

```
1. DB DDL 실행 (vr_withdraw_request_his 컬럼 추가)
2. relay-server 배포 (/relay/hecto/result 엔드포인트 orgTrdDt 처리)
3. api 배포 (PENDING Guard 패턴 적용)
4. 3pl-platform-batch 배포 (복구 배치 활성화)
```
