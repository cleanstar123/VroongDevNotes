## 1. 해결 방향 결정

### 근본 문제

Hecto API 성공 후 DB 저장 시 RDS가 불가 상태이면 기록이 영구 소실된다.
`vr_withdrl_list`(W), `vr_account_mst`(W/F) INSERT와 `vr_withdraw_request_his` INSERT가
모두 하나의 `@Transactional` 내에 묶여 있어, 후반부 DB 작업 실패 시 전체가 롤백되었다.

### 1차 시도 — W/F INSERT 이동 (롤백됨)

W/F INSERT를 Hecto 호출 이후로 이동하고 전부 REQUIRES_NEW 독립 커밋하는 방식으로 먼저 시도했으나,
배포 후 출금 오작동이 발생하여 롤백하였다.

**원인:** 기존 W/F INSERT는 `@Transactional` 내에서 비관적 락(`SELECT FOR UPDATE`)을 획득한 직후
잔액을 차감하는 역할을 겸하고 있었다. 이를 REQUIRES_NEW로 분리하면서 락 범위와 잔액 검증 순서가 틀어져
이중 출금 방지 로직이 무력화될 위험이 있었다.

### 최종 해결 전략 — PENDING breadcrumb + 예외 분리

**W/F INSERT 위치는 그대로 유지**하고, 예외 처리 구조만 변경한다.

```
[Hecto 호출 전]
  1. mchtTrdNo 생성 (generateMchtTrdNo)
  2. PENDING breadcrumb 독립 커밋 (REQUIRES_NEW)
     → mchtTrdNo를 미리 DB에 확보, 복구 배치가 fxResult 조회에 사용

[W/F INSERT — 기존 위치 유지]
  3. vr_withdrl_list(W), vr_account_mst(W) INSERT  ← 메인 @Transactional 내
  4. vr_withdrl_list(F), vr_account_mst(F) INSERT  ← 메인 @Transactional 내

[Hecto API 호출]
  5. requestWithdrawal(accountNum, bankCode, amt, accName, mchtTrdNo)
  6. Hecto 실패 시 → 예외 re-throw → 메인 트랜잭션 롤백 (W/F 롤백, 정상 동작)

[Hecto 성공 후 — 예외 분리]
  7. withdrawRequestLogService.save(COMPLETED 로그) [REQUIRES_NEW]
  8. withdrawRequestLogService.updateStatus(pendingSeqNo, "COMPLETED") [REQUIRES_NEW]
  9. updateWithrawReqSeqNo()
  ← 7~9 실패 시: 예외 catch + 로그만 출력, re-throw 금지 → W/F 커밋 보장

[복구 배치 — 5분 주기, 3pl-platform-batch]
  PENDING/UNKNOWN 레코드 중 10분 경과 건 조회
  → W 레코드 존재 시: COMPLETED (W/F는 이미 커밋됨)
  → W 레코드 없음: Hecto fxResult 조회
     - status=21 또는 isSuccess(): UNKNOWN + CRITICAL 알림 (수동 개입 필요)
     - status=22: FAILED
     - status=23: CANCELLED
     - status=29: 건너뜀, 다음 배치 재시도
```

**핵심 차이:** Hecto 성공 이후의 DB 실패는 W/F 커밋을 막지 않는다.
PENDING breadcrumb은 "이 거래가 Hecto에 제출됐다"는 증거만 남기며, 복구 배치의 fxResult 조회에 활용된다.

## 4. 핵심 구현 상세

### 4-1. PENDING breadcrumb 저장 (Hecto 호출 직전)

`WithdrawRequestLogService.savePending()` — `REQUIRES_NEW`로 독립 커밋.

```
[requestWithdrl @Transactional]
  ├── getWithdrlAccountInfoWithLock()   ← 비관적 락 획득
  ├── 잔액/수수료/프로모션 검증
  ├── vr_withdrl_list(W) INSERT          ← 메인 트랜잭션 (기존 위치 유지)
  ├── vr_account_mst(W) INSERT           ← 메인 트랜잭션
  ├── vr_withdrl_list(F) INSERT          ← 메인 트랜잭션
  ├── vr_account_mst(F) INSERT           ← 메인 트랜잭션
  ├── [신규] generateMchtTrdNo()
  ├── [신규] savePending() [REQUIRES_NEW] ← DB 커밋 ①
  ├── requestWithdrawal(..., mchtTrdNo).block()
  │     Hecto 실패 → re-throw → 메인 트랜잭션 롤백 (W/F 롤백)
  │     Hecto 성공 → ↓
  ├── save(COMPLETED 로그) [REQUIRES_NEW]   ← DB 커밋 ② (실패 시 catch + 로그만)
  ├── updateStatus(pendingSeqNo, "COMPLETED") [REQUIRES_NEW] ← DB 커밋 ③ (실패 시 catch + 로그만)
  └── updateWithrawReqSeqNo()              ← (실패 시 catch + 로그만)
  → 메인 트랜잭션 커밋 → W/F 확정
```

### 4-2. PENDING 이중 출금 방지 체크

**시나리오:** Hecto 성공 → DB 장애 → W/F 롤백 → 잔액 그대로 → 배치 실행 전 사용자가 재출금 클릭 → 이중 송금 위험

비관적 락 획득 직후, W/F INSERT 전에 PENDING 레코드를 확인하여 차단한다.

```java
// requestWithdrl() — getWithdrlAccountInfoWithLock() 직후
if (mobWithdrlQueryDslRepository.hasPendingWithdrawRequest(accountId)) {
    throw new RuntimeException("이전 출금 요청이 처리 중입니다. 잠시 후 다시 시도해주세요.");
}
```

**PENDING 차단이 올바른 이유:**

| 상태 | W/F | 잔액 | PENDING 차단 결과 |
|------|-----|------|-----------------|
| Hecto 실패 → W/F 롤백 | 없음 | 그대로 | ✅ 차단 (이중 출금 방지) |
| Hecto 성공, 로그 저장 실패 → W/F 커밋 | 있음 | 차감됨 | ⚠️ 차단되지만, 어차피 잔액 부족으로 중복 출금 불가. 배치가 10분 내 COMPLETED 처리 |

**UNKNOWN은 차단 대상이 아닌 이유:** UNKNOWN은 복구 배치가 이미 한 번 확인한 상태이므로
10분 이상 경과 후의 상태다. 배치 처리 이후 UNKNOWN 상태가 남아 있다면 관리자 개입이 필요한 케이스이며,
이 상태로 사용자 출금을 영구 차단하는 것은 부적절하다.

### 4-3. 예외 처리 분리 (핵심 변경)

```java
// Hecto API 호출 — 실패 시 re-throw (W/F 롤백, 정상 동작)
HectoWithdrawalResponseDto withdrawalResponse;
try {
    withdrawalResponse = hectoPaymentWebClient
        .requestWithdrawal(accountNum, bankCode, withrawAmt, accName, mchtTrdNo)
        .block();
} catch (Exception e) {
    throw e instanceof RuntimeException ? (RuntimeException) e
        : new RuntimeException("헥토 출금 요청에 실패했습니다.", e);
}

if (!"0000".equals(withdrawalResponse.getOutRsltCd())) {
    throw new RuntimeException("헥토 출금 요청 실패: ...");  // W/F 롤백
}

// Hecto 성공 이후 — DB 실패 시 re-throw 금지 (W/F 커밋 보장)
Long withdrawRequestHisSeqNo = null;
try {
    withdrawRequestHisSeqNo = withdrawRequestLogService.save(withdrawRequestLog);
    if (pendingSeqNo != null) {
        withdrawRequestLogService.updateStatus(pendingSeqNo, "COMPLETED");
    }
} catch (Exception e) {
    log.error("헥토 응답 로그 저장 실패 (출금 성공, W/F 커밋 유지): mchtTrdNo={}", mchtTrdNo, e);
    // re-throw 없음 — W/F는 메인 트랜잭션에서 커밋됨
}
```

### 4-3. 복구 배치 흐름 (`WithdrawalRecoveryUseCase`)

```
1. findUnresolvedWithdrawRequests(now - 10분) → PENDING/UNKNOWN 건 최대 100건 조회
2. 각 건에 대해:
   a. findWithdrawRequestHisBySeqNo(seqNo) → 상태 재확인 (이중 처리 방지)
   b. existsWithdrlWRecordByReqIdAndDate(reqId, orgTrdDt) → W 레코드 존재 여부
      - 존재: updateStatus(seqNo, "COMPLETED") → 종료
      - 없음: queryResult(mchtTrdNo, orgTrdDt) 호출
        - isSuccess() → UNKNOWN + [CRITICAL] 로그 (W 레코드 없이 Hecto 성공 → 수동 확인)
        - "22" → FAILED
        - "23" → CANCELLED
        - "29" → 건너뜀 (다음 배치 재시도)
        - 기타/오류 → UNKNOWN
```

> **CRITICAL 케이스 설명:** Hecto에서 성공(status=21)인데 W 레코드가 없는 상황은
> Hecto는 실제로 송금했는데 우리 W/F가 롤백된 것이므로, 라이더 잔액과 실제 지급 간 불일치가 발생한 상태다.
> 자동 재삽입 대신 수동 확인 후 처리한다.

## 5. fxResult API 검토

### 요청 파라미터

| 파라미터 | Max.Len | 설명 | 구현 |
|---------|---------|------|------|
| `mchtId` | 12 | 상점아이디 | ✅ 전송 |
| `mchtTrdNo` | 100 | 원거래 상점 거래번호 | ✅ PENDING 저장 시 확보한 값 사용 |
| `orgTrdDt` | 8 | 원거래일자 | ✅ `pending.getInsDate()` 기반 (yyyyMMdd) |

### 실제 관측 코드 (vr_withdraw_request_his 기준)

B9(fxTransKrw) 응답에서 확인된 실제 코드. fxResult(V1)도 같은 `outStatCd`/`outRsltCd` 구조를 공유한다.

| OUT_STAT_CD | OUT_RSLT_CD | OUT_RSLT_MSG | 의미               |
| ----------- | ----------- | ------------ | ---------------- |
| `0021`      | `0000`      | 정상처리         | 송금 성공            |
| `0031`      | `PY11`      | 은행 점검시간      | 일시적 실패           |
| `0031`      | `PY21`      | 수취인 계좌 없음    | 계좌 오류 실패         |
| `0031`      | `PY98`      | 상점주문번호 중복    | mchtTrdNo 재사용 오류 |
| `0031`      | `0404`      | 입금 한도 초과     | 한도 실패            |
| `0031`      | `0407`      | 총금액 상위       | 금액 제한 실패         |
| `0031`      | `0034`      | 법적제한계좌/지급정지  | 계좌 제한 실패         |
| `0031`      | `0438`      | 압류금지 전용 계좌   | 계좌 제한 실패         |
| `0031`      | `0413`      | 기타 수취 불가     | 기타 실패            |

### 응답 판정 우선순위 (복구 배치)

fxResult 응답 판정은 `status` 필드 단독이 아니라, `outStatCd`를 먼저 확인한 후 `status`로 세분화한다.

| 조건 | 의미 | 처리 |
|------|------|------|
| `outStatCd=0031` | Hecto가 해당 mchtTrdNo를 알지 못함 (거래 미등록) | **FAILED** (1순위 판정) |
| `isSuccess()` = true | `status=21` 또는 `outStatCd=0021 && outRsltCd=0000` | **UNKNOWN + CRITICAL 로그** (W 없음 → 수동 개입) |
| `status=22` | 송금 실패 (확정) | **FAILED** |
| `status=23` | 송금 취소 (확정) | **CANCELLED** |
| `status=29` | 은행 처리 중 (미확정) | 건너뜀, 다음 배치 재시도 |
| 기타 | 미정의 상태 | **UNKNOWN** |

> **`outStatCd=0031` 우선 판정 이유:** fxResult에서 0031이 반환되면 Hecto 측에 해당 거래가 존재하지 않거나
> 조회 자체가 실패한 것이므로, `status` 필드 값과 무관하게 FAILED로 확정할 수 있다.

### 문서 샘플의 `"status":"0"` 오기 방어

```java
// HectoResultQueryResponseDto.isSuccess()
public boolean isSuccess() {
    return "21".equals(status)
        || ("0021".equals(outStatCd) && "0000".equals(outRsltCd));
}
```

## 6. 정상 출금 흐름 검토

### 트랜잭션 구조

```
메인 @Transactional
  ├── 비관적 락 (SELECT FOR UPDATE) ← 이중 출금 방지 핵심
  ├── W/F INSERT (잔액 차감)         ← 락 범위 내, 기존 위치 유지
  ├── PENDING 저장 [REQUIRES_NEW]   ← 독립 커밋
  ├── Hecto 호출                     ← 실패 시 메인 tx 롤백 → W/F 롤백
  └── 로그 저장/갱신 [REQUIRES_NEW]  ← 실패해도 메인 tx 커밋 → W/F 확정
```

### 동시 요청 시뮬레이션

```
요청A: getWithdrlAccountInfoWithLock() → 비관적 락 획득
요청B: getWithdrlAccountInfoWithLock() → 락 대기
요청A: W/F INSERT (잔액 차감) → PENDING → Hecto → 로그 저장 → 메인 tx 커밋 → 락 해제
요청B: 락 획득 → 잔액 재조회 (A의 차감 반영됨) → 잔액 부족 → 예외 또는 계속
```

이중 출금 불가. ✅

### 장애 시나리오별 결과

| 장애 시점 | W/F 상태 | PENDING 상태 | 재출금 시도 시 | 복구 |
|----------|----------|-------------|--------------|------|
| PENDING 저장 전 예외 | 롤백 | 없음 | 재시도 가능 | - |
| PENDING 저장 후 Hecto 호출 전 예외 | 롤백 | PENDING | **차단** | fxResult → outStatCd=0031 → FAILED |
| Hecto 통신 오류/타임아웃 (re-throw) | 롤백 | PENDING | **차단** | fxResult 결과에 따라 처리 |
| Hecto 실패 (outRsltCd ≠ 0000) | 롤백 | PENDING | **차단** | fxResult → status=22 → FAILED |
| Hecto 성공 후 로그 저장 실패 | **커밋** | PENDING | **차단** (최대 10분, 배치가 COMPLETED 처리) | W 레코드 확인 → COMPLETED |
| 정상 완료 | 커밋 | COMPLETED | 재시도 가능 | - |

## 10. 2026-09-09 추가 구현 — VTIM 대응 및 중복 출금 방지 강화

### 10-1. vr_withdraw_request_his 단일 레코드 방식으로 변경

**변경 전 (2026-08-06 계획):**

PENDING 레코드 저장(Hecto 호출 전) + Hecto 성공 후 `save(COMPLETED 로그)` [별도 INSERT, REQUIRES_NEW] → 1건당 레코드 2개 생성.

**변경 후 (실제 배포):**

PENDING 레코드를 Hecto 호출 전에 저장한 뒤, Hecto 응답 후 해당 레코드를 **in-place UPDATE**한다.
INSERT는 1회뿐이며 레코드는 1건만 남는다.

```
savePending(pendingLog)                     → STATUS='PENDING', Hecto 데이터 없음
          ↓
requestWithdrawal(..., mchtTrdNo).block()   → Hecto 호출
          ↓
[성공] updateWithResponse(pendingSeqNo, {mchtId, trdNo, trdDt, trdTm,
                outStatCd, outRsltCd, outRsltMsg, bankCd, balance, status='COMPLETED'})
[VTIM] updateWithResponse(pendingSeqNo, {..., status='VTIM'})
[실패] updateWithResponse(pendingSeqNo, {..., status='FAILED'})
[예외] updateStatus(pendingSeqNo, 'FAILED')
```

이를 위해 `WithdrawRequestLogService`에 `updateWithResponse()` [REQUIRES_NEW] 추가,
`MobWithdrlQueryDslRepository`에 `updateWithdrawRequestHisStatus()` / `updateWithdrawRequestHisResponse()` 추가.

### 10-2. VTIM 전용 대응 패턴

헥토가 VTIM(은행 응답 지연, 이체 결과 미확정)을 반환하는 경우의 전용 처리 흐름.

#### 발생 시 즉시 처리

```
[MobWithdrlUseCase.requestWithdrl]
  ...
  Hecto 응답 → VTIM 판정
    ├── updateWithResponse(pendingSeqNo, {status='VTIM', ...})   [REQUIRES_NEW]
    ├── vtimPendingService.savePending(VrWithdrawVtimPendingEntity)  [REQUIRES_NEW]
    └── throw RuntimeException("헥토 출금 VTIM...")
         → 메인 트랜잭션 롤백 → W/F INSERT 롤백
         → 라이더 잔액 그대로 유지
         → 앱에 "이전 출금 건의 처리 결과를 확인 중입니다." 메시지 표시
```

`vr_withdraw_vtim_pending`에 PENDING 레코드가 남으며, `vr_withdraw_request_his`의 STATUS는 'VTIM'.

#### 배치 재조회 (60초 주기)

`VtimPendingCheckTasklet` → `POST /api/v1/vtim/process-pending` → `VtimPendingCheckUseCase.processAllPending()`

```
STATUS='PENDING'인 vr_withdraw_vtim_pending 전체 조회
  각 건:
    queryTransactionResult(mchtTrdNo, trdNo, trdDt).block()
      status=21 → VtimPendingLedgerService.createLedgerAndMarkSuccess(pending)
                   → W/F 원장 INSERT + vr_account_mst 차감 + STATUS='SUCCESS'
      status=22/23 → STATUS='FAILED'
      status=29    → retryCount+1 (다음 배치 재시도)
      예외/기타     → retryCount+1 (EX 또는 ERR:XX)
```

#### 만료 처리 및 이메일 알림

`MAX_RETRY_COUNT = 10`. 어느 경로(status=29, 예외, 기타)로든 retryCount+1 후 10에 도달하면:
- `STATUS='EXPIRED'`
- `[Vroong 긴급] VTIM 출금 건 수동 확인 필요` 이메일 발송
- 수신자: `vroong.notification.vtim.recipients` 설정값

> ⚠️ **2026-09-09 버그 수정:** 최초 구현 시 catch 블록과 else 브랜치에 MAX_RETRY_COUNT 체크가 없어,
> 예외 또는 예상치 못한 status 경로로 retryCount가 10을 초과해도 EXPIRED 처리 및 이메일이 발송되지 않았다.
> catch / else 브랜치에도 동일한 만료 처리를 추가하여 수정 완료.

### 10-3. VTIM PENDING 이중 출금 방지

VTIM 발생 후 배치 확인 전 사이에 라이더가 앱을 재시작하면 잔액이 원래대로 보인다
(W/F 롤백으로 `vr_account_mst`에 차감이 없기 때문).
이 상태에서 재출금 시도를 차단하기 위해 `requestWithdrl()` 진입 시 두 가지 체크를 수행한다.

```java
// 1. vr_withdraw_vtim_pending 체크 (VTIM 처리 중 차단)
if (vtimPendingRepository.existsByRiderIdAndStatus(riderId, "PENDING")) {
    throw new RuntimeException(
        "이전 출금 건의 처리 결과를 확인 중입니다. 잠시 후 다시 시도해주세요. (통상 1~2분 내 자동 처리)");
}

// 2. vr_withdraw_request_his 체크 (PENDING breadcrumb 처리 중 차단)
if (mobWithdrlQueryDslRepository.hasPendingWithdrawRequest(accountId)) {
    throw new RuntimeException("이전 출금 건이 처리 중입니다. 잠시 후 다시 시도해주세요.");
}
```

두 체크 모두 비관적 락 획득 직후, W/F INSERT 전에 위치한다.

### 10-4. 프론트엔드 중복 클릭 방지 및 에러 UX 개선

#### 중복 출금 방지 4중 체계 (`useWithdrawal.ts`)

| 계층 | 방법 | 설명 |
|------|------|------|
| 1 | 버튼 `disabled` | `isRequesting=true`이면 버튼 비활성화 |
| 2 | `isRequesting` state 체크 | handleWithdrawalSubmit 진입 즉시 체크 |
| 3 | `isRequestingRef` (useRef) | state 업데이트 이전에도 즉시 차단 (동기) |
| 4 | 2초 디바운스 | `lastRequestTimeRef` 기준, 2초 이내 재요청 차단 |

#### 에러 메시지 표시 위치 수정 (`WithdrawalPage.tsx`)

**변경 전:** `requestError` state를 출금 신청 모달 본문에 표시.
- 문제: React 비동기 state 업데이트로 인한 stale closure — `result === null && requestError` 조건이 실제 에러가 있어도 false로 평가될 수 있었음.

**변경 후:**
- `lastErrorMessageRef` (useRef) — 모든 에러 경로에서 동기적으로 기록. stale closure 문제 없음.
- `confirmPopupError` state — 출금 확인 팝업 내부에 에러 메시지 표시.
- "출금제한" 포함 메시지는 별도 `restrictionNotice` 전용 팝업으로 분기.

```tsx
// handleWithdrawalSubmit (비동기 호출 후)
if (result === null) {
    const errorMsg = lastErrorMessageRef.current || '출금 신청에 실패했습니다.';
    if (errorMsg.includes("출금제한")) {
        setRestrictionNotice(errorMsg);
        setShowConfirmPopup(false);
    } else {
        setConfirmPopupError(errorMsg);   // 확인 팝업 내 표시
    }
    return;
}
```
