# Vpay 신규 라이더 비밀번호 설정 버그

- **발생일**: 2026-09-04
- **영향 범위**: Vpay 앱 — 비즈사이트에 등록되었지만 아직 Vpay에 한 번도 로그인하지 않은 신규 라이더
- **증상**: 비밀번호 설정 페이지에서 비밀번호를 입력해도 계정이 생성되지 않고 로그인 화면으로 튕겨남
- **관련 사례**: `anhil00` 라이더 — 정상 경로로 비밀번호 설정이 안 돼 수동 회원가입 탭으로 우회함

---

## 비개발자를 위한 이해 설명

### 신규 라이더가 Vpay에 처음 로그인할 때 어떻게 되어야 하나요?

1. 관리자가 **비즈사이트**에서 라이더를 등록합니다 → 이때 DB의 `vr_rider_info` 테이블에 라이더 정보가 저장됩니다.
2. 라이더가 **Vpay 앱**을 열고 자신의 아이디로 로그인을 시도합니다.
3. 아직 비밀번호를 설정한 적이 없으므로, 앱이 **"비밀번호 설정 화면"** 으로 자동 이동합니다.
4. 라이더가 이메일 주소와 새 비밀번호를 입력하고 확인 버튼을 누릅니다.
5. DB의 `vr_user_info` 테이블에 계정 정보가 새로 생성되고, 이후부터는 정상적으로 로그인이 됩니다.

### 실제로는 어떤 일이 일어났나요?

**버그 1**: 로그인 버튼을 누르면 비밀번호 설정 화면이 잠깐 보이다가 **로그인 화면으로 튕겨나가는** 현상이 발생했습니다.

**버그 2**: 간신히 비밀번호 설정 화면에 머물더라도, 비밀번호를 입력하고 확인 버튼을 눌렀을 때 계정이 생성되지 않고 다시 **로그인 화면으로 이동**되었습니다.

결과적으로 신규 라이더는 Vpay에 정상적으로 로그인할 수 없었습니다.

### 왜 이런 일이 일어났나요? (쉬운 설명)

앱이 "이 사람이 로그인한 상태냐?"를 판단하는 기준에 문제가 있었습니다.

- **버그 1**: 비밀번호 설정 페이지로 이동하기 전에, 앱이 라이더를 "이미 로그인한 사람"으로 잘못 인식했습니다. 그 결과 앱이 로그인한 사람을 배달 화면으로 보내려 했고, 토큰(출입증)이 없으니 서버가 거부해서 다시 로그인 화면으로 돌아갔습니다.

- **버그 2**: 비밀번호 설정 화면에서 버튼을 눌렀을 때, 앱이 라이더의 아이디(userId)를 찾는 위치를 한 군데만 확인했는데, 실제로 아이디는 다른 위치에 저장되어 있었습니다. 찾지 못하니 "다시 로그인하세요"라며 로그인 화면으로 보내버렸습니다.

## 로직직 기술 상세

### 관련 파일 (프로젝트 : vroong-3pl-platform-app)

| 파일 | 역할 |
|------|------|
| `src/features/login/hooks/useLogin.ts` | 로그인 처리 훅 |
| `src/features/login/hooks/usePasswordSetup.ts` | 비밀번호 설정 처리 훅 |
| `src/app/AppRoutes.tsx` | 라우팅 및 GuestRoute, ProtectedRoute 정의 |
| `src/core/contexts/AuthContext.tsx` | 전역 인증 상태 (userId, userType) |

### 배경 지식

- `vr_rider_info`: 비즈사이트에서 등록한 라이더 정보 테이블
- `vr_user_info`: Vpay 앱 로그인 계정 정보 테이블 (비밀번호 포함)
- 신규 라이더는 `vr_rider_info`에는 있지만 `vr_user_info`에는 없음
- 백엔드는 이 경우 `{ success: true, requiresPasswordSetup: true }`를 반환 (accessToken 없음)
- `GuestRoute`: 이미 로그인한 사용자가 `/login`에 접근하면 `/delivery`로 보내는 가드

## 버그 1 — GuestRoute 잘못된 리다이렉트

### 증상
로그인 버튼을 누르면 배달 화면이 잠깐 깜빡이다가 로그인 화면으로 돌아옴

### 원인 코드 (`useLogin.ts` — 수정 전)

```typescript
// handleRiderLogin 내부 로직입니다.
if (response.success) {
    // ...

    // ❌ 문제: requiresPasswordSetup 체크보다 먼저 setAuth()가 호출됨.
    saveAuthData(rememberMe, response.accessToken, response.refreshToken, userInfo, userId, 'rider');
    setAuth(userId, 'RIDER', response.suppType || '');  // AuthContext에 userId 즉시 저장.

    if (response.requiresPasswordSetup) {
        setError(null);
        navigate('/password-setup');  // 여기서 이동을 시도하지만...
        return;
    }
}
```

### 실행 흐름 (버그 발생 시)

```
setAuth(userId, 'RIDER', '') 호출
    │
    ▼
AuthContext 상태 변경 → React 리렌더링 발생
    │
    ▼
GuestRoute가 AuthContext 변경 감지
  getUserInfo() → sessionStorage에서 riderId 발견
  isLoggedIn = true
    │
    ▼
<Navigate to="/delivery?tab=summary" /> 렌더링 → URL = /delivery
    │
    ▼
navigate('/password-setup') 가 실행되기 전에 /delivery가 먼저 적용됨
    │
    ▼
DeliveryPage 렌더링 → API 호출 → 토큰 없음 → 401 Unauthorized
    │
    ▼
401 인터셉터: /delivery는 NO_AUTH_REQUIRED 아님 → window.location.href = '/login'
```

### 핵심 문제
`setAuth()` → AuthContext 상태 변경 → GuestRoute 리렌더 → `<Navigate to="/delivery">` 가
`navigate('/password-setup')` 보다 먼저 실행되어 최종 URL이 `/delivery`가 됨.
`requiresPasswordSetup=true`일 때는 **토큰이 없으므로** 인증된 사용자로 취급하면 안 됨.

### 수정 코드 (`useLogin.ts` — 수정 후)

```typescript
if (response.success) {
    loginAttemptTracker.reset();
    setLockStatus(loginAttemptTracker.getStatus());

    // ✅ requiresPasswordSetup 분기를 최우선으로 처리
    // setAuth/saveAuthData를 호출하지 않아 GuestRoute가 isLoggedIn=true로
    // 판단해 /delivery로 리다이렉트하는 것을 방지
    if (response.requiresPasswordSetup) {
        sessionStorage.setItem('userId', userId);  // 비밀번호 설정 페이지에서 읽을 용도
        setError(null);
        navigate('/password-setup');
        return;
    }

    // 여기부터는 정상 로그인 처리
    sessionStorage.removeItem('maintenance_acknowledged');
    sessionStorage.removeItem('maintenance_acknowledged_seqno');

    const userInfo: any = {
        riderId: userId,
        requiresPasswordSetup: false,
        prmCode: response.prmCode,
    };

    if (response.userName) {
        userInfo.riderName = response.userName;
    }

    saveAuthData(rememberMe, response.accessToken, response.refreshToken, userInfo, userId, 'rider');
    setAuth(userId, 'RIDER', response.suppType || '');

    if (response.prmCode === 'A') {
        navigate('/adminHome');
    } else {
        navigate('/home');
    }
}
```

### 수정 포인트 요약
- `requiresPasswordSetup` 분기를 `saveAuthData()` / `setAuth()` **앞으로** 이동
- `requiresPasswordSetup=true`일 때는 `sessionStorage`에 `userId`만 저장하고 이동 (AuthContext에 인증 상태 등록하지 않음)

## 버그 2 — userId 저장소 불일치

### 증상
비밀번호 설정 화면에서 확인 버튼을 눌러도 계정이 생성되지 않고 로그인 화면으로 이동 됨

### 원인 코드 (`usePasswordSetup.ts` — 수정 전)

```typescript
// handlePasswordSetup 내부

// ❌ 문제: localStorage만 확인. rememberMe=false이면 userId는 sessionStorage에 있음
const userId = localStorage.getItem('userId') || '';

if (!userId) {
    setError('사용자 정보를 찾을 수 없습니다. 다시 로그인해주세요.');
    navigate('/login');  // ← userId를 못 찾으면 무조건 로그인으로 튕김
    return;
}
```

### 왜 불일치가 생기나?

`useLogin.ts`의 `saveAuthData()` 함수:

```typescript
const saveAuthData = (rememberMe, accessToken, refreshToken, userInfo, userId, loginType) => {
    if (rememberMe) {
        localStorage.setItem('userId', userId);    // 자동 로그인 체크 시: localStorage
        // ...
    } else {
        sessionStorage.setItem('userId', userId);  // 자동 로그인 미체크 시: sessionStorage
        // ...
    }
};
```

버그 1 수정 이후에는 `requiresPasswordSetup=true` 시 `saveAuthData()`를 호출하지 않고
`sessionStorage.setItem('userId', userId)`를 직접 호출하므로, 항상 `sessionStorage`에 저장됨.

비밀번호 설정 페이지에서 `localStorage`만 읽으면 당연히 빈 값이 되어 로그인 화면으로 튕김.

### 수정 코드 (`usePasswordSetup.ts` — 수정 후)

```typescript
// ✅ localStorage → sessionStorage 순서로 모두 확인
const userId = localStorage.getItem('userId') || sessionStorage.getItem('userId') || '';

if (!userId) {
    setError('사용자 정보를 찾을 수 없습니다. 다시 로그인해주세요.');
    navigate('/login');
    return;
}
```

그리고 비밀번호 설정 성공 시:

```typescript
// 수정 전 (문제)
const userInfoStr = localStorage.getItem('userInfo');
let userInfo: any = {};
// ... riderId 없이 저장, setAuth() 미호출

// ✅ 수정 후
const userInfo: any = {
    riderId: userId,           // 이후 ProtectedRoute의 isLoggedIn 판단에 필요
    requiresPasswordSetup: false,
};
if (response.userName) {
    userInfo.riderName = response.userName;
}
localStorage.setItem('userInfo', JSON.stringify(userInfo));

localStorage.removeItem('userId');
sessionStorage.removeItem('userId');  // sessionStorage도 정리

setAuth(userId, 'RIDER', '');  // AuthContext에 정상 로그인 상태 등록 → /home 이동 가능
navigate('/home');
```

### 수정 포인트 요약
- `userId` 읽기: `localStorage || sessionStorage` 순서로 모두 확인
- 성공 후 `userInfo`에 `riderId` 포함하여 localStorage에 저장 (ProtectedRoute의 `isLoggedIn` 판단 기준)
- 성공 후 `setAuth()` 호출하여 AuthContext에 인증 상태 등록 (없으면 /home 접근 불가)
- `sessionStorage`의 `userId`도 함께 삭제

## 수정 후 정상 흐름

```
1. 신규 라이더 로그인 시도
        ↓
2. 백엔드: { success: true, requiresPasswordSetup: true } 반환 (토큰 없음)
        ↓
3. useLogin.ts: requiresPasswordSetup 감지
   → setAuth/saveAuthData 호출 없음 (GuestRoute가 isLoggedIn=true로 잘못 인식하는 것 방지)
   → sessionStorage에 userId만 저장
   → navigate('/password-setup')
        ↓
4. 비밀번호 설정 화면 정상 표시 (리다이렉트 없음)
        ↓
5. 라이더가 이메일 + 비밀번호 입력 후 확인 버튼 클릭
        ↓
6. usePasswordSetup.ts: sessionStorage에서 userId 정상 조회
   → 백엔드 /api/v1/mob/login/password-setup 호출
        ↓
7. 백엔드:
   - vr_user_info INSERT (계정 생성)
   - vr_rider_pre_his INSERT (선정산 설정)
   - vr_rider_info.PRE_ACCT_YN = 'Y' 업데이트
   - 기본 수수료 자동 부여
   - JWT 토큰 생성 후 반환
        ↓
8. 프론트엔드: 토큰 저장, setAuth() 호출, navigate('/home')
        ↓
9. 로그인 완료 ✅
```
