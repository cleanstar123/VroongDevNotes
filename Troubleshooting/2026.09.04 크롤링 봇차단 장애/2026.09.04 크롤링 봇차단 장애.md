> [!info] 시스템 구성 배경
>
> - **Fast API 모드**: 릴레이 서버(ECS Fargate)가 자체 IP로 `api-deliverycenter.baemin.com` 직접 호출 (Puppeteer fetch)
> - **BrightData Fallback**: Fast API 실패 시 주거형 프록시(brd.superproxy.io)로 동일 API 재시도
> - **릴레이 서버**: Java 백엔드의 배민 크롤링 요청을 중계, ECS Fargate에서 운영
> - **배치**: Spring Batch `riderDeliveryHistoriesNowTasklet`이 10분마다 `/api/v1/delivery/status` 호출

## 2. 원인 분석 — 연쇄 장애 구조

> [!warning] 장애 연쇄 흐름
>
> ```
> [07:02] 배민, 릴레이 서버 자체 IP/브라우저 지문 차단
>         → Fast API 500 시작
>         ↓
> [07:02~10:04] BrightData 주거형 프록시 fallback 정상 처리
>              → 크롤링 약 3시간 정상 유지
>         ↓
> [10:00] 배치 152개 협력사 동시 요청
>         → 릴레이 서버 큐 과부하 시작
>         ↓
> [10:05] BrightData IP 대역도 배민 차단 (or 요청 한도 초과)
>         → BrightData 502 반환
>         → Fast API + BrightData 모두 실패
>         ↓
> [11:21] 릴레이 큐 완전 포화 (RELAY_QUEUE_FULL)
>         → 배민이 이상 접근 감지, SMS 2FA 요청
>         → SMS 웹훅 처리 실패 → 세션 강제 만료
>         ↓
> [11:46] ECS 태스크 종료 (응답시간 67,438ms → 메모리/타임아웃)
>         ↓
> [12:00~] 활성 세션 없음
>          → Java 백엔드 IllegalArgumentException → 400 즉각 실패
> ```

> [!info] 핵심 원인 3가지
>
> **1. 봇 차단 방식의 차이**
> - Fast API (고정 IP + Chrome/Puppeteer) → 배민이 IP/브라우저 지문 감지하여 500 반환
> - BrightData (주거형 프록시, 유동 IP) → 처음엔 200 통과, 이후 IP 대역 차단
>
> **2. 대량 동시 배치의 위험성**
> - 152개 협력사를 동시 요청하는 구조가 BrightData까지 소진시킴
> - 요청 집중 → BrightData 요청 한도 초과 or 배민 이상 감지 가속화
>
> **3. 봇 차단 감지 누락**
> - 현재 릴레이 서버(`auto-reauth.js`)는 **403만 봇 차단으로 인식**
> - Fast API 500 → BrightData 200 패턴은 봇 차단으로 인식하지 못하고 **조용히 fallback**
> - 07:02 차단 시 즉각 알림이 없어 3시간 후 대규모 장애로 확대
