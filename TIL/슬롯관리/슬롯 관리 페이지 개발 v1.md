# 슬롯 관리 페이지 개발 v1

## 개요

부릉 라이더 대시보드에서 협력사별 슬롯 달성 목표를 유연하게 관리하기 위한 **슬롯 정책 관리 페이지**를 신규 개발하였다.
기존에는 공통코드 `SLOTINFO` (SLOT1~SLOT4)의 VAL1~VAL7 값이 모든 협력사에 동일하게 적용되었으나, 협력사마다 특성이 다르기 때문에 협력사별 맞춤 슬롯 정책이 필요하다는 고객사 요구가 발생하였다.

## 기본 슬롯 체계 (SLOTINFO 공통코드)

슬롯 정책이 매칭되지 않는 협력사에는 기존 SLOTINFO 기본값이 적용된다.

| 슬롯 | 시간대 | 표시명 |
|------|--------|--------|
| SLOT1 | 06:00 ~ 12:59 | 아침점심피크 |
| SLOT2 | 13:00 ~ 16:59 | 오후논피크 |
| SLOT3 | 17:00 ~ 19:59 | 저녁피크 |
| SLOT4 | 20:00 ~ 02:59 | 심야논피크 |

SLOTINFO의 VAL1~VAL7은 요일별(1=월~7=일) **세트당 목표 건수**이다.
최종 목표 = `VAL × slotSetCnt` (협력사의 라이더 세트 수)

## 사용법

### 1. 정책 등록

1. 슬롯 관리 메뉴 진입 → **신규 등록** 버튼 클릭
2. 모달에서 다음 항목 입력:
   - **그룹명**: 필수. 정책 식별용 이름 (예: 안성A)
   - **협력사명 LIKE 패턴**: 협력사명 매칭 패턴 (예: `%안성A%`)
     - 입력 시 500ms 디바운스 후 매칭 표준권역 자동 조회
   - **우선순위**: 동일 협력사에 여러 정책이 매칭될 때 높은 숫자 우선
   - **적용 시작일**: yyyyMMdd 형식. **비워두면 즉시 적용** (모달 내 안내 문구 표시)
   - **필수 달성 슬롯 수**: 달성 필요 슬롯 수 (DB 저장, 향후 활용)
   - **수락률**: 수락률 조건 (DB 저장, 향후 활용)
   - **대시보드+ 여부**: Y/N
   - **사용 여부**: Y(사용) / N(미사용)
   - **표준권역**: 쉼표 구분. LIKE 패턴 입력 시 자동 조회
3. **슬롯 설정** 섹션에서 슬롯별 목표 건수 설정:
   - 슬롯명, 시작/종료 시간 개별 입력
   - VAL1~VAL7: 요일별(월~일) 목표 건수 입력
   - **VAL을 0으로 입력** → 해당 슬롯은 달성 목표 없음 (대시보드에 `—` 표시)
   - **+ 슬롯 추가** 버튼으로 슬롯 행 추가 가능

### 2. 정책 목록 확인

- 목록 테이블의 **적용 시작일** 컬럼:
  - 날짜 미설정 → `즉시 적용` 표시
  - 날짜 설정 → `YYYY-MM-DD` 형식 표시
- 수정 버튼 클릭 시 기존 값이 모달에 로드됨

## 설정값에 따른 대시보드 결과

### 정책 매칭 로직

대시보드 조회 시 각 날짜마다 아래 순서로 협력사 목표치 결정:

```
1. 조회 날짜 기준 applyStartDate <= 날짜 이고 USE_YN='Y'인 정책 필터
2. 협력사명이 LIKE_PATTERN에 매칭되는 정책 필터 (Java regex 변환 후 대소문자 무시)
3. applyStartDate DESC → priority DESC 정렬 후 1번째 정책 선택
4. 매칭 정책 없으면 SLOTINFO 기본값 사용 (× slotSetCnt 적용)
```

### 주요 케이스

| 상황 | 대시보드 목표값 |
|------|----------------|
| 정책 매칭 O | 정책 VAL1~VAL7 값 (× 1, slotSetCnt 미적용) |
| 정책 매칭 X | SLOTINFO VAL × slotSetCnt |
| 동일 협력사 여러 정책 | priority 높은 정책 적용 |
| applyStartDate 이전 날짜 조회 | 해당 날짜에 유효한 정책 적용 (날짜별 분기) |
| VAL = 0인 슬롯 | 대시보드에 `—` 표시, 달성률 분모/분자에서 제외 |

### slotSetCnt 적용 차이

- **SLOTINFO 기본값**: 목표 = `VAL × slotSetCnt` (협력사의 세트 수만큼 배수)
- **신규 정책**: 목표 = `VAL` 그대로 (관리자가 최종값을 직접 입력)

## 날짜별 정책 이력 관리

정책 교체 시 기존 정책을 삭제하지 않고 **새 정책을 applyStartDate와 함께 등록**한다.

```
예시:
- 정책A: likePattern=%아산A%, applyStartDate=20250101
- 정책B: likePattern=%아산A%, applyStartDate=20260801 (8월부터 목표 상향)

7월 31일 조회 → 정책A 적용
8월 01일 조회 → 정책B 적용 (applyStartDate가 더 최근)
```

이력이 자동으로 보존되어 과거 데이터를 조회해도 당시 정책이 정확히 반영된다.

- 모달 UI에서 입력/저장 가능
- 현재는 DB 저장만 되며 대시보드 달성률 계산에 실제 반영되지 않음
- 향후 활용 예정

### ⑦ 신규 슬롯 정책 적용일: 과거 데이터 오류 방지를 위해 정책 적용 일자 반영

**반영 완료**

- `vr_slot_policy.APPLY_START_DATE` 컬럼에 적용 시작일 저장 (yyyyMMdd)
- 대시보드 조회 시 **날짜별**로 `applyStartDate <= 해당날짜`인 정책 중 가장 최근 적용일 정책 선택
- 조회 기간 내 정책 변경이 있어도 날짜별로 다른 정책 자동 분기

**동작 원리**:
```
7/21~27 조회, 7/25 새 정책 등록 시
  → 7/21~24: 이전 정책 (applyStartDate 더 이전인 것)
  → 7/25~27: 새 정책 자동 적용
```

**정책 이력 관리**: 정책 수정 시 기존 정책을 삭제하지 않고 새 정책 등록. USE_YN=Y 유지로 과거 조회 시 이력 보존.

**UI**: 적용일 미입력 시 "비워두면 오늘부터 즉시 적용됩니다" 안내 표시. 목록에서는 "즉시 적용" 표기.

**백엔드 처리 위치**: `DashboardQueryDslRepository.resolveSupplierTargetsForDate()`

---

### ⑧ 신규 슬롯 반영, 표준 권역 선택: 선택 시(복수 가능) 기본 슬롯에서 해당 슬롯 제외

**반영 완료**

- `vr_slot_policy_area` 테이블에 정책-표준권역 매핑 저장

- LIKE 패턴 입력 시 `GET /api/v1/slot-policy/preview-areas` API로 매칭 표준권역 자동 조회 및 자동 입력 (500ms 디바운스)
- 복수 표준권역 쉼표 구분 입력 가능

## 주요 개발 포인트

### LIKE 패턴 → Java Regex 변환

SQL LIKE의 `%`, `_`를 Java 정규식으로 변환하여 협력사명 매칭 수행:

```java
private boolean suppNameMatchesPattern(String suppName, String likePattern) {
    String regex = likePattern
        .replace(".", "\\.")
        .replace("%", ".*")
        .replace("_", ".");
    return suppName.matches("(?i)" + regex);
}
```

DB JOIN 대신 Java 레벨에서 처리하여 정책 수 대비 성능 유지.

### slotSetCnt 처리 이원화

- **SLOTINFO 기본값 사용 시**: `목표 = VAL × slotSetCnt` (레퍼런스 동일 여부로 판단)
- **신규 정책 사용 시**: `목표 = VAL` (관리자가 최종값 직접 입력)

```java
Map<String, Map<Integer, Long>> targets =
    resolveSupplierTargetsForDate(suppName, date, policyCache, slotTargets);
long effectiveSetCnt = (targets == slotTargets) ? slotSetCnt : 1L;
```

### 날짜별 정책 캐싱 전략

조회 기간의 `toDate` 이전에 시작된 모든 정책을 한 번에 로드한 뒤, 각 날짜·협력사 조합마다 스트림 필터링으로 적합한 정책을 결정한다.

DB 쿼리는 1회, Java 레벨에서 날짜별 분기 처리 → N+1 문제 없음.
