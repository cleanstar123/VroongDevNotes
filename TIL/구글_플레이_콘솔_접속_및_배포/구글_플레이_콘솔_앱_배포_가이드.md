## 0. 배포 순서 필수 준수 — 반드시 내부 테스트부터

> ### 절대 원칙: 프로덕션 직접 배포 금지
>
> **AAB를 플레이 콘솔에 업로드할 때는 반드시 내부 테스트 트랙에 먼저 올려야 합니다.**
> 프로덕션에 바로 올리지 마세요.

### 올바른 배포 순서

```
① 내부 테스트 출시
      ↓ (이상 없음 확인 후)
② 버전 승급 → 공개 테스트 출시
      ↓ (이상 없음 확인 후)
③ 버전 승급 → 프로덕션 출시
      ↓
④ 내부 테스터를 제외한 전체 사용자에게 배포 완료
```

### 단계별 체크포인트

| 단계 | 트랙 | 확인 사항 | 다음 액션 |
|------|------|-----------|-----------|
| ① | 내부 테스트 | 앱 설치 및 핵심 기능 정상 동작 확인 | 우측 상단 **버전 승급** 클릭 |
| ② | 공개 테스트 | 구글 검토 완료 후 실제 사용 환경 검증 | 우측 상단 **버전 승급** 클릭 |
| ③ | 프로덕션 | 전체 공개 — 내부 테스터 외 모든 사용자 다운로드 가능 | — |

> **왜 이 순서를 지켜야 하는가?**
> - 내부 테스트는 구글 검토가 수 분 이내로 끝나 빠른 검증이 가능합니다.
> - 문제가 있는 버전이 프로덕션에 올라가면 전체 사용자에게 영향이 가고, 롤백해도 이미 설치된 기기는 즉시 되돌아가지 않습니다.
> - **버전 승급**을 활용하면 동일한 AAB를 재업로드하지 않고 트랙만 이동시킬 수 있습니다.

## 1. 구글 플레이 콘솔 접속


### 접속 방법

1. 구글 플레이 콘솔 공식 주소: `https://play.google.com/console`
2. 개발자 계정으로 로그인 (Google 계정)
3. 좌측 사이드바 → **앱** 목록에서 배포할 앱 클릭

### 앱 대시보드 구성

| 메뉴             | 설명                              |
| -------------- | ------------------------------- |
| 앱 대시보드         | 앱 전반적인 현황 (다운로드 수, 평점, 충돌 등)    |
| 출시             | 배포 트랙 관리 (프로덕션, 베타, 알파, 내부 테스트) |
| Android Vitals | 앱 성능 지표 (ANR, 충돌률 등)            |
| 수익 창출          | 인앱 구매, 구독 관리                    |
| 사용자 및 권한       | 팀 멤버 접근 권한 관리                   |
| 정책 상태          | 구글 정책 준수 여부                     |

## 2. AAB(Android App Bundle) 빌드

> 이 프로젝트는 **React + Capacitor** 구조이므로, Android Studio GUI가 아닌 PowerShell에서 명령어로 빌드합니다.

### 빌드 전 준비: versionCode / versionName 업데이트 (필수)

`android/app/build.gradle` 파일에서 수정:

```gradle
android {
    defaultConfig {
        versionCode 52          // 정수, 매 배포마다 반드시 1 이상 증가
        versionName "3.2.2"     // 사용자에게 표시되는 버전명
    }
}
```

> **주의:** `versionCode`는 플레이스토어에 이미 업로드된 값보다 반드시 높아야 합니다. 같거나 낮으면 업로드 오류 발생.

### PowerShell에서 빌드 (전체 순서)

프로젝트 루트(`C:\wonjun\vroong-3pl-platform-app`)에서 PowerShell을 열고 순서대로 실행:

```powershell
# 1단계: React 웹 앱 빌드
npm run build

# 2단계: 빌드 결과물을 Android 프로젝트에 동기화 (Capacitor)
npx cap sync android

# 3단계: Android AAB 빌드 (Gradle)
cd android
.\gradlew bundleRelease
```

### 빌드 결과물 위치

```
android/app/build/outputs/bundle/release/app-release.aab
```

이 `.aab` 파일을 플레이 콘솔에 업로드합니다.

### 각 단계 설명

| 단계 | 명령어 | 설명 |
|------|--------|------|
| 1 | `npm run build` | React 소스를 `build/` 폴더로 컴파일 |
| 2 | `npx cap sync android` | `build/` 결과물을 `android/app/src/main/assets/`에 복사 + 플러그인 동기화 |
| 3 | `.\gradlew bundleRelease` | Gradle로 서명된 AAB 파일 생성 |

### 서명 설정 (이미 구성 완료)

`android/app/build.gradle`에 release 서명이 설정되어 있어 별도 작업 불필요:

```gradle
signingConfigs {
    release {
        storeFile file('vroong-release.keystore')
        keyAlias 'vroong-key'
        // storePassword, keyPassword 설정됨
    }
}
```

## 3. 배포 트랙 선택

### 트랙 종류 및 용도

| 트랙 | 대상 | 설명 |
|------|------|------|
| **내부 테스트** | 최대 100명 (내부 테스터) | 가장 빠른 검토 (몇 분 이내), 팀 내부 검증용 |
| **비공개 테스트 (알파)** | 특정 사용자 그룹 | 외부 테스터 대상, 구글 검토 후 배포 |
| **공개 테스트 (베타)** | 선택한 비율 또는 전체 | 일반 사용자도 참여 가능, 구글 검토 필요 |
| **프로덕션** | 전체 사용자 | 실제 스토어에 공개, 단계적 출시 가능 |

### 트랙 선택 경로

```
앱 선택 → 좌측 메뉴 → 출시 → 아래 중 선택
  └── 테스트 → 내부 테스트
  └── 테스트 → 비공개 테스트
  └── 테스트 → 공개 테스트
  └── 프로덕션
```

## 4. 새 릴리즈 생성

1. 원하는 트랙 메뉴로 이동 (예: 프로덕션)
2. 우측 상단 **새 릴리즈 만들기** 버튼 클릭
3. Google Play 앱 서명 설정 확인
   - 처음 배포 시: Google Play에 앱 서명 키 등록 필요
   - 이후 배포 시: 자동으로 이전 서명 키 사용

### Google Play 앱 서명 (App Signing)

- Google이 서명 키를 보관·관리하는 방식
- 업로드 키(upload key)로 AAB를 서명 → Google이 배포 시 실제 앱 서명 키로 재서명
- 권장 방식: 키 분실/유출 시 Google에 요청하여 복구 가능

## 5. AAB 업로드 및 릴리즈 정보 입력

### AAB 업로드

1. **앱 번들 추가** 버튼 클릭
2. 빌드한 `.aab` 파일 드래그&드롭 또는 파일 선택
3. 업로드 완료 대기 (파일 크기에 따라 수 초~수 분)
4. 업로드 후 자동으로 아래 정보 표시:
   - versionCode / versionName
   - 지원 기기 수
   - 최소 SDK 버전

### 릴리즈 이름 (선택)

- 관리용 식별 이름, 사용자에게는 노출되지 않음
- 예: `1.2.0 (2026-09-10)`

### 출시 노트 작성 (필수 권장)

- 사용자에게 표시되는 업데이트 내용
- 언어별 작성 가능 (한국어 기본 작성 권장)

```
예시:
- 버그 수정 및 성능 개선
- 출금/송금 버튼 야간 시간대 비활성화 기능 추가 (23:50 ~ 00:05)
- 안정성 향상
```

## 6. 검토 및 출시

### 검토 전 체크리스트

- [ ] versionCode가 이전보다 높은지 확인
- [ ] 출시 노트 작성 완료
- [ ] AAB 파일 오류 없이 업로드됨
- [ ] 대상 국가/지역 설정 확인

### 단계적 출시 (프로덕션 한정)

프로덕션 트랙의 경우 전체 사용자에게 한 번에 배포하지 않고 단계적으로 출시 가능:

```
출시 비율 설정 예시:
  1% → 문제 없으면 → 5% → 10% → 50% → 100%
```

- 출시 비율 변경: 해당 릴리즈 → **단계적 출시 업데이트** 클릭
- 문제 발생 시: **출시 중단** 클릭으로 즉시 롤백 가능 (이전 버전으로 복귀)

### 검토 및 출시 버튼

| 버튼 | 동작 |
|------|------|
| 검토하기 | 입력 내용 최종 확인 화면으로 이동 |
| 프로덕션에 출시 | 구글 검토 후 실제 배포 시작 |

### 구글 검토 소요 시간

| 트랙 | 검토 시간 |
|------|-----------|
| 내부 테스트 | 수 분 ~ 1시간 |
| 비공개/공개 테스트 | 수 시간 ~ 1일 |
| 프로덕션 (첫 출시) | 1~3일 |
| 프로덕션 (업데이트) | 수 시간 ~ 1일 |

## 7. 버전 승급 — 트랙 간 이동 방법

> 동일한 AAB를 재업로드할 필요 없이, 이미 업로드한 버전을 상위 트랙으로 승급시킵니다.

### 버전 승급 절차

**내부 테스트 → 공개 테스트 승급:**

```
좌측 메뉴 → 테스트 → 내부 테스트
→ 해당 릴리즈의 우측 상단 [버전 승급] 클릭
→ [공개 테스트] 선택
→ 출시 노트 확인 후 [출시 검토] → [공개 테스트 출시] 클릭
```

**공개 테스트 → 프로덕션 승급:**

```
좌측 메뉴 → 테스트 → 공개 테스트
→ 해당 릴리즈의 우측 상단 [버전 승급] 클릭
→ [프로덕션] 선택
→ 출시 노트 확인 후 [출시 검토] → [프로덕션 출시] 클릭
```

### 프로덕션 출시 후 결과

- **내부 테스터:** 내부 테스트 트랙을 통해 이미 설치한 버전 유지
- **일반 사용자 전체:** 구글 플레이 스토어에서 새 버전 다운로드 가능

## 8. 배포 상태 확인

### 상태 확인 경로

```
앱 대시보드 → 출시 → 프로덕션 (또는 해당 트랙)
```

### 릴리즈 상태 종류

| 상태 | 설명 |
|------|------|
| 검토 중 | 구글이 앱을 검토하는 중 |
| 출시됨 | 배포 완료, 사용자 다운로드 가능 |
| 단계적 출시 | 일부 비율에만 배포 중 |
| 출시 중단 | 배포 일시 중단 |
| 거부됨 | 구글 정책 위반으로 거부, 수정 후 재제출 필요 |

### 배포 후 확인 사항

- 플레이스토어 앱 페이지에서 버전 업데이트 표시 확인
- Android Vitals에서 충돌률 모니터링
- 사용자 리뷰/평점 모니터링

## 9. 주요 주의사항

### versionCode 관리

- 한번 업로드한 versionCode는 **재사용 불가**
- 업로드 실패해도 해당 versionCode는 소모되지 않음 (단, 구글 서버에 도달한 경우 소모될 수 있음)
- 팀 협업 시 versionCode 충돌 방지를 위해 배포 전 항상 확인

### 키스토어 관리

- 키스토어 파일(`.jks`)과 비밀번호는 **절대 분실 금지**
- Google Play 앱 서명을 사용하는 경우에도 업로드 키 백업 필수
- 키스토어는 코드 저장소(Git)에 커밋하지 말 것

### 배포 전 테스트 순서 (반드시 준수)

```
① 내부 테스트 출시 → 기능 검증
② 버전 승급 → 공개 테스트 출시 → 검증
③ 버전 승급 → 프로덕션 출시
```

→ 자세한 내용은 [0. 배포 순서 필수 준수](#0-배포-순서-필수-준수--반드시-내부-테스트부터) 참고

### 긴급 롤백 방법

1. 플레이 콘솔 → 해당 트랙 → 해당 릴리즈
2. **출시 중단** 클릭 → 이전 버전으로 자동 복귀
3. 근본 원인 수정 후 새 versionCode로 재배포
