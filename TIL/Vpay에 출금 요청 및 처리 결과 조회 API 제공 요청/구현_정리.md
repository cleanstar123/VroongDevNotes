## 5. 핵심 설계 결정사항

### 5-1. 비동기 처리 (`@Async`)
- 클라이언트에게 HTTP 202를 즉시 반환하고, 헥토 호출은 별도 스레드에서 처리
- `VroongApiApplication`에 `@EnableAsync` 추가
- `processWithdrawalAsync`는 상태가 ACCEPTED가 아니면 early return → 중복 트리거 방지

#### 중복 트리거 방지가 필요한 이유

동일한 requestId로 두 요청이 거의 동시에 들어오면 `processWithdrawalAsync`가 두 번 호출될 수 있다.

```
[스레드 A - 1번 요청]                  [스레드 B - 2번 요청, 거의 동시]
acceptWithdrawal()
  → PESSIMISTIC_WRITE 락 획득
  → 없음 → ACCEPTED로 저장
  → 락 해제
                                    acceptWithdrawal()
                                      → PESSIMISTIC_WRITE 락 획득
                                      → 기존 레코드 발견 (status=ACCEPTED)
                                      → 내용 일치 → 그대로 반환
                                      → 락 해제

processWithdrawalAsync() 호출          processWithdrawalAsync() 호출
  → 헥토 송금 API 호출 !!!              → 헥토 송금 API 호출 !!!
```

가드 없으면 두 스레드가 모두 헥토에 송금 요청을 보내는 **이중 송금**이 발생한다.

#### 가드 동작 방식

```java
// processWithdrawalAsync 진입 시 status 확인
if (!"ACCEPTED".equals(entity.getStatus())) {
    log.info("processWithdrawalAsync 스킵 ...");
    return;   // 이미 처리 중이면 조용히 종료
}

// 통과하면 즉시 PROCESSING으로 변경 → 두 번째 진입 차단
entity.setStatus("PROCESSING");
jpaRepository.save(entity);
```

```
[스레드 A]                              [스레드 B]
status 확인 → "ACCEPTED" → 통과
status = "PROCESSING" 저장
헥토 호출 시작                           status 확인 → "PROCESSING" → early return ✓
```

#### 이 상황이 실제로 발생하는 케이스

| 케이스 | 설명 |
|---|---|
| 클라이언트 네트워크 재시도 | 응답을 못 받고 같은 요청을 재전송 |
| 로드밸런서 이중 전달 | 타임아웃 직전 두 서버 인스턴스에 동시 도달 |
| 서버 재시작 후 배치 복구 | ACCEPTED 상태로 남은 건을 배치가 재처리 시도 |

금융 송금 로직이므로 실제 발생 빈도와 무관하게 이중 실행 방어 코드를 반드시 넣어야 한다.

### 5-2. 멱등성 보장
- `REQUEST_ID` UNIQUE 제약 + PESSIMISTIC_WRITE 락 (`findByRequestIdWithLock`)
- 동일 requestId 재요청 → 내용 일치 여부 확인 후 기존 결과 반환
- 내용 불일치 → `IDEMPOTENCY_CONFLICT` (409)
- 동일 withdrawalId에 다른 requestId → `WITHDRAWAL_ID_CONFLICT` (409)

#### requestId vs withdrawalId 역할 구분

| 필드             | 생성 주체     | 의미                              |
| -------------- | --------- | ------------------------------- |
| `requestId`    | 부릉 클라이언트  | "이 API 호출"의 고유번호 (네트워크 재시도 식별용) |
| `withdrawalId` | 부릉 내부 시스템 | "이 출금 건"의 원번호 (실제 지급해야 할 건 식별용) |

하나의 출금 건(`withdrawalId`)에 대해 API를 여러 번 호출할 수 있고, 그 각각의 호출마다 `requestId`가 붙는 구조다.

#### IDEMPOTENCY_CONFLICT — 동일 requestId + 내용 불일치

```
1번 요청: requestId=REQ-001, withdrawalId=WD-001, amount=10,000원
  → DB 저장, ACCEPTED

2번 요청: requestId=REQ-001, withdrawalId=WD-001, amount=99,999원  ← 금액이 다름
  → IDEMPOTENCY_CONFLICT (409)
```

"REQ-001이라는 호출은 이미 10,000원짜리로 처리했는데, 같은 번호로 99,999원이 들어왔다"는 의미다.
클라이언트 버그나 데이터 변조 가능성이 있으므로 거부한다. 정상 재시도라면 내용이 동일해야 하고, 동일하면 기존 결과를 그대로 반환한다.

#### WITHDRAWAL_ID_CONFLICT — 동일 withdrawalId + 다른 requestId

```
1번: requestId=REQ-001, withdrawalId=WD-001, amount=10,000원
  → DB 저장, SUCCEEDED (이미 송금 완료)

2번: requestId=REQ-002, withdrawalId=WD-001, amount=10,000원  ← requestId만 다름
  → WITHDRAWAL_ID_CONFLICT (409)
```

"WD-001이라는 출금 건은 이미 REQ-001로 처리 완료했는데, 새 requestId로 다시 요청이 들어왔다"는 의미다.
이를 허용하면 동일한 출금 건을 두 번 송금하게 된다.

#### 두 제약이 모두 필요한 이유

| 제약 | 막는 것 |
|---|---|
| `requestId` 체크만 있으면 | 부릉이 새 requestId를 생성해 보내는 것만으로 중복 송금 가능 |
| `withdrawalId` 체크만 있으면 | 같은 requestId로 내용을 바꿔 보내는 변조를 잡을 수 없음 |

두 제약이 함께 있어야 "같은 건을 두 번 보내는 것"과 "동일 호출을 다른 내용으로 바꾸는 것" 모두 차단된다.

#### 정상 재시도 — 동일 requestId + 동일 내용

가장 흔하고 정상적인 시나리오다. 클라이언트가 응답을 못 받아서 같은 요청을 다시 보내는 경우다.

```
클라이언트 → POST /api/v1/withdrawals (requestId=REQ-001, amount=10,000원)
                    ↓
              서버에서 정상 처리 중...
                    ↓
        (네트워크 타임아웃 또는 연결 끊김)
                    ↓
클라이언트 → 응답을 못 받았음 → "실패한 건가?" → 같은 요청 재전송
         → POST /api/v1/withdrawals (requestId=REQ-001, amount=10,000원) ← 완전히 동일
```

requestId(멱등성 키)를 쓰는 이유 자체가 이 케이스를 안전하게 처리하기 위한 것이다. 내용이 동일하면 서버는 기존 레코드를 그대로 반환하고 헥토 호출을 추가로 하지 않는다. 클라이언트는 현재 처리 상태를 응답으로 받아 폴링을 이어간다.

#### 세 케이스 최종 정리

| 상황 | 결과 | 의미 |
|---|---|---|
| requestId 동일 + 내용 동일 | 기존 결과 반환 (정상) | 클라이언트가 응답을 못 받고 재시도한 것 |
| requestId 동일 + 내용 다름 | 409 IDEMPOTENCY_CONFLICT | 같은 번호인데 내용이 달라 → 버그 또는 변조 |
| requestId 다름 + withdrawalId 동일 | 409 WITHDRAWAL_ID_CONFLICT | 이미 처리한 출금 건을 새 번호로 또 요청 → 이중 송금 시도 |

### 5-3. mchtTrdNo 사전 저장
- 헥토 호출 **전에** DB에 mchtTrdNo를 저장 → 서버 재시작 후 배치 복구 가능
- 형식: `EW + yyyyMMddHHmmssSSS + 3자리 난수` (총 22자)
- UNIQUE 제약으로 중복 생성 방지

### 5-4. VTIM/PENDING_CONFIRMATION 처리 (A안)
- 최대 재시도 횟수 초과 시 FAILED로 자동 전환하지 않음
- PENDING_CONFIRMATION 상태 유지 + 알림 메일 발송
- 관리자가 헥토에 직접 확인 후 수동 DB 반영

### 5-5. 계좌번호 보안
- DB 저장: `AesEncryptionUtils.encrypt()` (AES-GCM)
- 헥토 전송: 복호화 후 AES-256-ECB 재암호화 (기존 로직 재사용)
- API 응답: 복호화 후 뒤 4자리만 노출 (`*****1234`)
- 로그: 계좌번호 직접 출력 없음

### 5-6. X-API-Key 인증 필터
- `@Order(-99)` — `ApiSecretFilter(-100)` 이후 적용
- `/api/v1/withdrawals/**` 경로에만 적용
- `ApiSecretFilter` whitelist에 동일 경로 추가 (Secret 인증 우회)
- 프로퍼티: `vroong.external.api.key: ${VROONG_EXTERNAL_API_KEY}`

### GET /api/v1/withdrawals/{requestId} — 결과 조회

**Response 200**
```json
{
  "requestId": "REQ-20261019-0001",
  "status": "SUCCEEDED",
  "final": true,
  "version": 3,
  "nextPollAfterSeconds": null,
  "completedAt": "2026-10-19T12:00:05+09:00"
}
```

**nextPollAfterSeconds 기준**

| 상태 | 값 |
|---|---|
| ACCEPTED | 5 |
| PROCESSING | 10 |
| SUCCEEDED / FAILED / PENDING_CONFIRMATION | null |

### 오류 응답 형식
```json
{
  "error": {
    "code": "IDEMPOTENCY_CONFLICT",
    "message": "동일한 requestId로 내용이 다른 요청이 존재합니다."
  },
  "traceId": "abc123"
}
```

| code | HTTP | 의미 |
|---|---|---|
| IDEMPOTENCY_CONFLICT | 409 | 동일 requestId, 다른 내용 |
| WITHDRAWAL_ID_CONFLICT | 409 | 동일 withdrawalId, 다른 requestId |
| NOT_FOUND | 404 | requestId 없음 |
| VALIDATION_ERROR | 400 | 입력값 오류 |
| UNAUTHORIZED | 401 | X-API-Key 없음/불일치 |

## 10. 트러블슈팅 기록

### 중복 트리거 문제
- 같은 requestId로 두 번 요청이 들어오면 두 개의 `processWithdrawalAsync`가 호출될 수 있음
- 해결: `acceptWithdrawal`의 PESSIMISTIC_WRITE 락으로 두 번째 요청은 기존 결과 반환
- 추가 방어: `processWithdrawalAsync` 시작 시 status == "ACCEPTED" 아니면 early return

### `saveAll` vs `save`
- 처음 `jpaRepository.saveAll(entity)` 호출 시 컴파일 오류
- `saveAll`은 `Iterable`을 받음 → `save(entity)`로 수정

### `@EnableAsync` 누락
- `processWithdrawalAsync`에 `@Async`를 붙였으나 동기로 동작
- `VroongApiApplication`에 `@EnableAsync` 추가하여 해결
