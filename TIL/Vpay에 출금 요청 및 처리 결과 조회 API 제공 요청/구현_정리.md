## 1. 작업 배경 및 합의 사항

부릉 사가 Vpay 서버를 통해 직접 출금(송금)을 요청하고 결과를 조회할 수 있는 API를 요청한 것.

| 항목 | 합의 내용 |

| 잔액/수수료 차감 | 없음 - 전달받은 금액을 최종 입금액으로 처리 |
| VTIM 처리 방식 | **A안**: PENDING_CONFIRMATION 유지, 수동 해결 (자동 FAILED 전환 없음) |

## 2. 신규 테이블 DDL

```sql
CREATE TABLE vpay_external_withdrawal (
    SEQ_NO           BIGINT         NOT NULL AUTO_INCREMENT COMMENT '일련번호 (PK)',
    REQUEST_ID       VARCHAR(100)   NOT NULL                COMMENT '부릉 요청 고유번호 (멱등성 키)',
    WITHDRAWAL_ID    VARCHAR(100)   NOT NULL                COMMENT '부릉 원출금 신청번호',
    TRANSFER_ID      VARCHAR(100)   NOT NULL                COMMENT 'Vpay 내부 고유 거래번호 (VT+UUID)',
    STATUS           VARCHAR(30)    NOT NULL                COMMENT 'ACCEPTED/PROCESSING/PENDING_CONFIRMATION/SUCCEEDED/FAILED',
    IS_FINAL         TINYINT(1)     NOT NULL DEFAULT 0      COMMENT '최종 확정 여부 (SUCCEEDED/FAILED=1)',
    VERSION          INT            NOT NULL DEFAULT 1      COMMENT '상태 변경 버전',
    TRANSFER_AMOUNT  DECIMAL(18,2)  NOT NULL                COMMENT '실 입금액 (원)',
    BANK_CODE        VARCHAR(10)    NOT NULL                COMMENT '은행 코드',
    ACCOUNT_NUMBER   VARCHAR(500)   NOT NULL                COMMENT '입금 계좌번호 (AES-256 암호화)',
    ACCOUNT_MEMO     VARCHAR(50)                            COMMENT '입금 적요',
    MCHT_TRD_NO      VARCHAR(100)   NOT NULL                COMMENT '헥토 상점 거래번호 (EW+yyyyMMddHHmmssSSS+3rand)',
    HECTO_TRD_NO     VARCHAR(64)                            COMMENT '헥토 거래번호 (응답값)',
    RESULT_CODE      VARCHAR(10)                            COMMENT '헥토 결과코드 (0000=성공, VTIM=타임아웃)',
    RESULT_MESSAGE   VARCHAR(255)                           COMMENT '헥토 결과 메시지',
    RETRY_COUNT      INT            NOT NULL DEFAULT 0      COMMENT '헥토 결과조회 재시도 횟수',
    LAST_CHECKED_AT  DATETIME                               COMMENT '마지막 결과조회 일시',
    COMPLETED_AT     DATETIME                               COMMENT '송금 완료 확정 일시',
    INS_DATE         DATETIME       NOT NULL                COMMENT '등록일시',
    INS_USER         VARCHAR(50)                            COMMENT '등록자',
    UPD_DATE         DATETIME                               COMMENT '수정일시',
    UPD_USER         VARCHAR(50)                            COMMENT '수정자',
    PRIMARY KEY (SEQ_NO),
    UNIQUE KEY uq_request_id (REQUEST_ID),
    UNIQUE KEY uq_withdrawal_id (WITHDRAWAL_ID),
    UNIQUE KEY uq_mcht_trd_no (MCHT_TRD_NO)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='부릉 외부 출금 요청 관리';
```

## 4. 상태 흐름

```
[클라이언트 POST /api/v1/withdrawals]
        ↓
    ACCEPTED  ← DB 저장 + HTTP 202 즉시 반환
        ↓ (비동기 @Async)
    PROCESSING  ← 헥토 fxTrnsmit 호출 전
        ↓
   ┌────┴─────────────────────────────────┐
   │ 0000 (성공)    VTIM (타임아웃)     기타 실패  │
   ↓               ↓                    ↓
SUCCEEDED    PENDING_CONFIRMATION      FAILED
(isFinal=true)  (isFinal=false)     (isFinal=true)
                   ↓
         [60초 배치 /fxResult 재조회]
                   ↓
         21(성공) → SUCCEEDED
         22/23(실패) → FAILED
         29(처리중) → retryCount++
         10회 초과 → PENDING_CONFIRMATION 유지 + 알림 메일
```

## 5. 핵심 설계 결정사항

### 5-1. 비동기 처리 (`@Async`)
- 클라이언트에게 HTTP 202를 즉시 반환하고, 헥토 호출은 별도 스레드에서 처리
- `VroongApiApplication`에 `@EnableAsync` 추가
- `processWithdrawalAsync`는 상태가 ACCEPTED가 아니면 early return → 중복 트리거 방지

### 5-2. 멱등성 보장
- `REQUEST_ID` UNIQUE 제약 + PESSIMISTIC_WRITE 락 (`findByRequestIdWithLock`)
- 동일 requestId 재요청 → 내용 일치 여부 확인 후 기존 결과 반환
- 내용 불일치 → `IDEMPOTENCY_CONFLICT` (409)
- 동일 withdrawalId에 다른 requestId → `WITHDRAWAL_ID_CONFLICT` (409)

### 5-3. mchtTrdNo 사전 저장
- 헥토 호출 **전에** DB에 mchtTrdNo를 저장 → 서버 재시작 후 배치 복구 가능
- 형식: `EW + yyyyMMddHHmmssSSS + 3자리 난수` (총 22자)
- UNIQUE 제약으로 중복 생성 방지

### 5-4. VTIM/PENDING_CONFIRMATION 처리 (A안)
- 최대 재시도 횟수 초과 시 FAILED로 자동 전환하지 않음
- PENDING_CONFIRMATION 상태 유지 + 알림 메일 발송
- 관리자가 헥토에 직접 확인 후 수동 DB 반영

### 5-5. 계좌번호 보안
- DB 저장: `AesEncryptionUtils.encrypt()` (AES-GCM)
- 헥토 전송: 복호화 후 AES-256-ECB 재암호화 (기존 로직 재사용)
- API 응답: 복호화 후 뒤 4자리만 노출 (`*****1234`)
- 로그: 계좌번호 직접 출력 없음

### 5-6. X-API-Key 인증 필터
- `@Order(-99)` — `ApiSecretFilter(-100)` 이후 적용
- `/api/v1/withdrawals/**` 경로에만 적용
- `ApiSecretFilter` whitelist에 동일 경로 추가 (Secret 인증 우회)
- 프로퍼티: `vroong.external.api.key: ${VROONG_EXTERNAL_API_KEY}`

## 6. API 명세

### POST /api/v1/withdrawals — 출금 접수

**Request Header**
```
X-API-Key: {부릉 전용 API Key}
Content-Type: application/json
```

**Request Body**
```json
{
  "requestId": "REQ-20261019-0001",
  "withdrawalId": "WD-20261019-0001",
  "transferAmount": "100000",
  "currency": "KRW",
  "bankCode": "020",
  "accountNumber": "1234567890",
  "accountMemo": "출금"
}
```

**Response 202**
```json
{
  "requestId": "REQ-20261019-0001",
  "withdrawalId": "WD-20261019-0001",
  "transferId": "VT3F8A1B2C4D5E6F7A8B",
  "status": "ACCEPTED",
  "final": false,
  "version": 1,
  "transferAmount": 100000,
  "currency": "KRW",
  "bankCode": "020",
  "maskedAccountNumber": "******7890",
  "accountMemo": "출금",
  "nextPollAfterSeconds": 5,
  "createdAt": "2026-10-19T12:00:00+09:00"
}
```

### GET /api/v1/withdrawals/{requestId} — 결과 조회

**Response 200**
```json
{
  "requestId": "REQ-20261019-0001",
  "status": "SUCCEEDED",
  "final": true,
  "version": 3,
  "nextPollAfterSeconds": null,
  "completedAt": "2026-10-19T12:00:05+09:00"
}
```

**nextPollAfterSeconds 기준**

| 상태 | 값 |
|---|---|
| ACCEPTED | 5 |
| PROCESSING | 10 |
| SUCCEEDED / FAILED / PENDING_CONFIRMATION | null |

### 오류 응답 형식
```json
{
  "error": {
    "code": "IDEMPOTENCY_CONFLICT",
    "message": "동일한 requestId로 내용이 다른 요청이 존재합니다."
  },
  "traceId": "abc123"
}
```

| code | HTTP | 의미 |
|---|---|---|
| IDEMPOTENCY_CONFLICT | 409 | 동일 requestId, 다른 내용 |
| WITHDRAWAL_ID_CONFLICT | 409 | 동일 withdrawalId, 다른 requestId |
| NOT_FOUND | 404 | requestId 없음 |
| VALIDATION_ERROR | 400 | 입력값 오류 |
| UNAUTHORIZED | 401 | X-API-Key 없음/불일치 |

## 10. 트러블슈팅 기록

### 중복 트리거 문제
- 같은 requestId로 두 번 요청이 들어오면 두 개의 `processWithdrawalAsync`가 호출될 수 있음
- 해결: `acceptWithdrawal`의 PESSIMISTIC_WRITE 락으로 두 번째 요청은 기존 결과 반환
- 추가 방어: `processWithdrawalAsync` 시작 시 status == "ACCEPTED" 아니면 early return

### `saveAll` vs `save`
- 처음 `jpaRepository.saveAll(entity)` 호출 시 컴파일 오류
- `saveAll`은 `Iterable`을 받음 → `save(entity)`로 수정

### `@EnableAsync` 누락
- `processWithdrawalAsync`에 `@Async`를 붙였으나 동기로 동작
- `VroongApiApplication`에 `@EnableAsync` 추가하여 해결
