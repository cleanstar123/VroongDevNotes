검토해 주신 내용 잘 받았습니다. 각 항목에 대해 검토 결과를 말씀드립니다.

1. 개발 가능 여부와 예상 일정
  요청하신 방식으로 개발 가능합니다. 신규 API 엔드포인트 추가와 테이블 변경이 필요하며, 기존 출금 기능에는 영향이 없도록 별도로 구현할 예정입니다. 원하시는 일정을 먼저 공유해 주시면 검토 후 가능 여부를 안내드리겠습니다.

2. 잔액·수수료 중복 차감 없이 송금만 수행 가능 여부
  가능합니다. 전달해 주시는 금액을 최종 입금액으로 간주하여 Vpay 서버 내에서 잔액 차감 및 수수료 계산 없이 헥토 송금만 처리하도록 분리 구현할 예정입니다. 예치금 흐름 추적을 위한 DB 기록은 별도 유형으로 유지됩니다.

3. 운영 및 테스트 API 주소
  개발 완료 후 별도로 안내드리겠습니다.

4. 인증 방식과 인증 정보 전달 방법
부릉 전용 API Key를 발급하여 아래와 같이 요청 헤더에 포함하는 방식으로 적용할 예정입니다.

POST /api/v1/withdrawals
Host: [Vpay 서버 주소]
Content-Type: application/json
X-API-Key: vpay_prod_xxxxxxxxxxxxxxxxxx

인증 정보는 개발 완료 후 안전한 채널을 통해 전달드리겠습니다.

5. 확정된 요청·응답 명세
  제안해 주신 명세를 대부분 수용하는 방향으로 검토하였습니다. 한 가지 확인이 필요한 부분이 있습니다.

  - accountMemo 필드는 헥토 송금 API의 입금 적요(custAcntSumry) 필드에 매핑됩니다. 헥토 측 길이 제한을 확인 중이며, 제한이 있을 경우 별도로 안내드리겠습니다.

 6. 처리 상태 및 오류 코드 정의
  제안하신 상태값(ACCEPTED / PROCESSING / PENDING_CONFIRMATION / SUCCEEDED / FAILED)과 오류 코드 체계를 수용합니다. 한 가지 협의가 필요한 사항이 있습니다.

  - 헥토 타임아웃(VTIM) 또는 통신 단절 발생 시 Vpay 서버는 자동으로 헥토 결과조회 API를 주기적으로 호출하여 송금 결과를 확인합니다. 대부분의 경우 수 회 이내에 결과가 확정되지만, 예외적으로 최대 재시도 횟수를 초과해도 결과가 확인되지 않는 경우가 발생할 수 있습니다. 이 시점에는 시스템이 자동으로 송금 여부를 확정할 수 없어 관리자의 수동 확인이 필요한 상태가 됩니다.

  이 경우 GET 조회 응답을 어떻게 처리할지 두 가지 방안 중 협의가 필요합니다.
  - A안 (권고): PENDING_CONFIRMATION 유지, final: false, nextPollAfterSeconds: null로 반환. 더 이상 자동 해소가 어려운 상태임을 알리고, 담당자 간 직접 확인을 통해 수동 처리. 실제 송금이 이루어졌을 가능성을 배제하지 않으므로 부릉 측에서도 미지급으로 자동 확정하지 않는 방식.
  -  B안: FAILED로 반환. 처리는 단순하지만 실제로 송금이 완료된 건을 미지급으로 처리할 위험이 있음.

  운영상 안전을 위해 A안을 권고드리며, 의견 부탁드립니다. 발생 빈도는 매우 낮으나 정책을 사전에 정해두는 것이 중요하다고 판단됩니다.

7. 권장 조회 주기와 호출 제한
  내부 검토 후 안내드리겠습니다. 초안 기준으로는 ACCEPTED/PROCESSING 상태에서 5~10초 주기, PENDING_CONFIRMATION 상태에서 30초 주기를 권장드릴 예정입니다.

8. 거래 보관 기간과 결과 조회 가능 기간
  현재 Vpay 서버는 거래 데이터에 대한 별도 삭제 정책이 없어 영구 보관됩니다. 따라서 결과 조회 기간에 별도 제한은 없습니다. 다만 향후 데이터 보관 정책 변경 시 사전에 안내드리겠습니다.
